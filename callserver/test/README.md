# 路径与信令测试脚本

用 Python 假客户端直接驱动服务端，验证信令闭环、路径仲裁状态机和 UDP 中继转发。
不依赖 Qt 客户端，也不依赖真实摄像头/麦克风，因此在任意一台能连到服务端的机器上
都能确定性地跑出同样结果。

## 运行

```bash
# 方式一：自动拉起服务端并跑全部场景（推荐）
python run_all.py --server-bin ../build/call_server

# 方式二：服务端已经在跑（例如线上 47.100.244.110:8889）
python run_all.py --no-server --host 47.100.244.110 --port 8889

# 单跑一个场景
python test_path_basic.py --host 127.0.0.1 --port 8889
```

整套约 1.5 分钟——场景 2/3 依赖服务端真实的 4s 超时、10s 冷却、3s 稳定窗口，
等待是预期行为，不是卡住。

## 场景一览

| 脚本 | 覆盖内容 | 断言数 |
|---|---|---|
| `test_signaling_basic.py` | 登录/用户列表、空用户名拒绝、**重名登录踢下线**、呼叫离线用户报错 | 6 |
| `test_path_basic.py` | UDP 端口观察、`Probing → P2pProbation → P2p` 全链路与 epoch 递增 | 8 |
| `test_path_reprobe_ok.py` | 打洞失败退中继 → 10s 冷却防抖 → 双方恢复直连后成功回切 P2P | 10 |
| `test_path_reprobe_fail.py` | 观察期内一方上报中断 → `report_timeout` 退回中继；单方面迟到上报不得切回 | 7 |
| `test_relay_media.py` | 中继端点学习、1200B/4000B 分片完整送达、未知 relayId 丢弃 | 10 |

## 这些脚本抓到过的真实缺陷

1. **重名登录导致信令发错人**（`test_signaling_basic.py`）
   服务端按用户名查找会话时取第一个匹配，早期允许重名登录，于是旧连接仍占据该
   用户名，呼叫信令被转发到已失效的连接上，新登录的一端什么都收不到。
   现改为重复登录先踢掉同名旧会话。

2. **中继接收缓冲 64B 截断媒体包**（`test_relay_media.py`）
   1200 字节的视频分片被截成 43 字节，表现为中继模式下画面静止/花屏。
   缓冲改为 4096B 后修复；脚本直接断言"发多少收多少"防回归。

## 设计约定

- 假客户端复用 `fake_client.py`，只实现协议必要部分，不复制服务端逻辑；
- 每个场景用**带运行标记的唯一用户名**，保证重复执行互不干扰；
- `wait_for(..., since=t)` 必须显式传时间下界——否则会把本场景早先收到的同类
  消息再次匹配上，造成假阳性（写场景 3 时踩过）；
- 断言粒度是"服务端下发的状态与原因"，不是"没崩就算过"。
